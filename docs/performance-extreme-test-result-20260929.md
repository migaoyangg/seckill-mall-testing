# 秒杀入口极限压力测试结果（2026-09-29）

## 测试目标

验证单机部署下秒杀入口在突发并发场景中的吞吐、响应时间、错误率和数据一致性，并观察性能拐点。本报告记录的是本机实测上限，不等同于生产环境容量上限。

## 测试环境

- 硬件：Mac17,5，6 核 CPU，8 GB 内存
- 操作系统：macOS 26.6.2
- 应用：Spring Boot 3.2.5，单实例，JVM `-Xms512m -Xmx1024m`
- Java：OpenJDK 21.0.11
- 数据库：MySQL 9.6.0
- 缓存与异步队列：Redis 8.8.0
- 压测工具：Apache JMeter 5.6.3
- 部署方式：应用、JMeter、MySQL 和 Redis 位于同一台主机
- 秒杀异步模式：Redis

## 测试方法

使用 `scripts/jmeter/seckill-entry.jmx` 请求 `POST /api/seckill/do/{goodsId}`。每名虚拟用户使用独立登录令牌，每档并发使用独立商品和秒杀活动，活动库存与并发用户数相等。

- 并发档位：100、250、500、1000、1500、2000
- 到达模型：1 秒内启动全部虚拟用户，每用户请求 1 次
- 成功条件：HTTP 状态为 200，业务码为 200，返回状态为 `PROCESSING`
- 一致性条件：订单数等于独立用户数，用户无重复下单，`初始库存 - 订单数 - MySQL 剩余库存 = 0`，异步队列最终清空
- 各档测试结束前等待异步消费完成，再停止活动并核对 MySQL 与 Redis 状态

前五档累计发起 3350 次秒杀请求并生成 3350 笔订单，未出现重复下单、库存差异或异步消息积压。2000 并发档虽然 2000 次请求均成功受理并生成 2000 笔订单，但活动结束后 MySQL 仍剩余 250 件库存，一致性差值为 -250，因此该档不满足数据一致性要求。

## 2000 并发异常分析

2000 并发档的请求错误率仍为 0%，但异步订单处理跨过了每 60 秒执行一次的库存预热时点。当前实现存在以下竞态：

1. `SeckillSchedule` 每 60 秒调用 `preheatAllActiveStock()`。
2. `SeckillStockServiceImpl.preheatStock()`读取 MySQL 中仍在异步扣减的阶段性库存。
3. `RedisUtils.preheatStock()`使用普通 `SET`，无条件覆盖 Redis 中已经完成预扣减的实时库存。
4. 活动结束时又把被覆盖后的 Redis 库存同步回 MySQL，最终形成 2000 笔订单但仍剩余 250 件库存的矛盾状态。

本轮流量在库存被覆盖前已经全部进入系统，因此没有生成超过初始库存的订单；但如果覆盖后仍有新请求进入，重置出来的库存可能被再次扣减，存在超卖风险。

## 结论

1. 当前单机环境在 1500 个突发并发用户下保持 0% 请求错误率和数据一致性；2000 并发时虽然接口仍为 0% 错误，但触发了库存预热与异步扣减的竞态，数据一致性不再成立。
2. 性能瓶颈首先体现在响应时间而非正确性。250 并发时 P95 已达到 906 ms；500 并发后 P95 超过 1.6 秒；1500 并发时 P95 为 4.117 秒。
3. 若以“错误率低于 1%、P95 不超过 1 秒、数据一致”为可接受标准，本机单实例的建议突发容量为 250 并发用户；500 并发开始进入明显延迟区间。
4. 以正确性为硬性标准，本轮已验证稳定上限为 1500 并发，首个失败档位为 2000 并发。修复定时预热覆盖实时库存的问题后，才能继续测试更高并发的性能极限。
