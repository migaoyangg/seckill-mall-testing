## 4. 需求范围

### 4.1 用户与权限

- 用户注册、登录、退出和个人信息查询。
- JWT 与 Redis 双重登录状态校验。
- 普通用户和管理员权限隔离。
- 无 Token、无效 Token、过期 Token及账号禁用处理。

### 4.2 商品管理

- 商品分页、搜索、详情、分类和状态查询。
- 管理员新增、修改、上下架和逻辑删除商品。
- 商品库存不足、商品下架和非法参数校验。
- 商品数据变更后的缓存失效与一致性处理。

### 4.3 秒杀活动

- 管理员创建、开启、结束、修改和删除秒杀活动。
- 秒杀活动开始时间、结束时间和活动状态校验。
- Redis Lua 原子执行限流、限购和库存预扣。
- Redis Queue 或 RabbitMQ 异步下单。
- 使用 `requestId` 查询异步处理结果。
- 消息发送或订单创建失败后的库存及用户标记回滚。

### 4.4 订单、支付与售后

- 普通订单和秒杀订单创建、查询及状态流转。
- 待支付订单取消和库存恢复。
- 支付及支付回调幂等。
- 已支付订单退款及重复退款保护。
- 普通订单和秒杀订单超时关闭。
- 支付、取消、退款和关单并发时的状态互斥。

### 4.5 非功能需求

- 秒杀入口在突发并发下不超卖、不重复下单。
- 异步消息不丢失、可重复消费且消费结果幂等。
- MySQL、Redis、订单和库存最终一致。
- 核心接口具备明确的响应时间、错误率和容量指标。
- 故障发生后能够定位、补偿和恢复。

## 5. 已确认的业务规则

### 5.1 通用规则

1. 接口统一返回 `code`、`message` 和 `data`。
2. 参数格式错误使用 HTTP 400 和业务码 `2001`。
3. 可识别的业务失败应返回明确业务码，不应直接产生未处理的 HTTP 500。
4. 用户只能查询和操作自己的订单及秒杀请求结果。
5. 管理功能只能由管理员访问，普通用户越权请求不得改变数据。

### 5.2 秒杀规则

1. 活动未开始返回 `4001`，活动已结束返回 `4002`。
2. 库存不足返回 `4003`，不能产生订单或负库存。
3. 同一用户对同一活动最多生成一笔有效秒杀订单。
4. 秒杀入口受理后返回 `requestId`，结果状态应从 `PROCESSING` 进入 `SUCCESS` 或 `FAIL` 终态。
5. 只有请求所属用户可以查询对应 `requestId`。
6. 入队失败或异步落单失败时，必须回滚 Redis 预扣库存和用户限购、重复请求标记。
7. 消息重复投递不能生成重复订单，也不能重复扣减库存。

### 5.3 订单状态规则

订单状态定义如下：

| 状态值 | 状态名称 | 允许的主要后续状态 |
| ---: | --- | --- |
| 0 | 待支付 | 已支付、已取消、超时关闭 |
| 1 | 已支付 | 退款中 |
| 4 | 已取消 | 终态 |
| 5 | 超时关闭 | 终态 |
| 6 | 退款中 | 已退款；失败时应回滚或允许安全重试 |
| 7 | 已退款 | 终态 |

同一订单在支付、取消和超时关闭并发发生时，只允许一个合法状态迁移成功。库存恢复操作必须幂等，任何订单都不能重复恢复库存。

### 5.4 数据一致性规则

1. 成功订单数不得超过活动初始库存。
2. 商品或活动库存不得出现负数。
3. 同一用户、同一秒杀活动的订单数不得超过一笔。
4. 活动结束后，MySQL 与 Redis 的最终库存必须一致。
5. 一致性校验应满足：`初始库存 - 成功订单数 - 剩余库存 = 0`。
6. 异步队列最终应被消费完毕，不得存在无处理结果的长期积压消息。

### 6.2 发现的问题和风险

| 编号 | 等级 | 问题 | 影响 | 处理要求 |
| --- | --- | --- | --- | --- |
| RR-001 | 阻断 | 定时库存预热使用 MySQL 阶段性库存无条件覆盖 Redis 实时库存 | 可能造成库存回增、账实不符，并在后续请求进入时形成超卖 | 修改预热机制，禁止活动进行中无条件覆盖已有 Redis 库存；修复后重新执行并发及一致性回归 |
| RR-002 | 高 | RabbitMQ 异步下单和延迟关单模式缺少完整实测 | 无法确认消息重复、延迟、失败重试和最终一致性是否满足要求 | 补充 RabbitMQ 模式功能、异常、重复消费和压力测试 |
| RR-003 | 高 | 支付、取消、退款和超时关单的并发竞争缺少充分实测 | 可能产生非法状态、重复退款或重复恢复库存 | 执行并发状态机测试，并直接核对数据库和库存结果 |
| RR-004 | 高 | Redis、数据库或消息队列故障注入覆盖不足 | 无法证明部分失败后的补偿和恢复能力 | 增加消息发送失败、消费失败、数据库更新失败和 Redis 短暂不可用测试 |
| RR-005 | 中 | 性能目标未形成面向生产部署规格的正式容量结论 | 本机数据不能直接代表生产容量 | 在目标部署环境重新进行容量测试并形成容量基线 |
| RR-006 | 中 | 长时间稳定性和积压恢复尚未形成完整证据 | 短时测试无法发现资源泄漏和长期消息堆积 | 执行持续压测，观察 JVM、数据库连接池、Redis、队列深度和恢复时间 |
| RR-007 | 低 | 部分历史测试记录的环境和执行时间不同 | 结论可能因代码或环境变化而失效 | 发布前在固定版本、固定环境中执行一次完整回归并归档证据 |

## 7. 性能与容量评审结论

现有单机 Redis 异步模式极限测试结果如下：

| 并发用户数 | 结果 |
| ---: | --- |
| 100 | 请求成功率和数据一致性通过，P95 约 399 ms |
| 250 | 请求成功率和数据一致性通过，P95 约 906 ms |
| 500 | 数据一致性通过，但 P95 约 1.679 s，进入明显延迟区间 |
| 1000 | 数据一致性通过，P95 约 2.542 s |
| 1500 | 数据一致性通过，P95 约 4.117 s |
| 2000 | 请求均被受理，但出现 250 件库存差异，不通过 |

若暂以“技术错误率低于 1%、P95 不超过 1 秒且数据一致”为验收标准，则当前本机单实例建议突发容量为 250 并发用户。该结论仅适用于对应测试环境，不等同于生产容量承诺。

## 8. 验收标准

### 8.1 功能验收

- 用户、商品、订单、秒杀和管理员主流程全部通过。
- 未登录、无效 Token、越权、非法参数及非法状态均被正确拒绝。
- 秒杀结果最终进入明确终态，不存在长期停留在 `PROCESSING` 的请求。
- 支付回调、退款、消息消费和超时关单满足幂等要求。

### 8.2 一致性验收

- 不得出现超卖、负库存或重复订单。
- MySQL 与 Redis 库存核对差值为 0。
- 订单和订单明细关系完整。
- 支付流水号唯一且不能绑定多个订单。
- 取消、退款和关单后库存只恢复一次。

### 8.3 性能验收

- 秒杀入口技术错误率低于 1%。
- 建议基线为 P95 不超过 1 秒；最终阈值需由产品、研发和运维根据部署规格共同确认。
- 压测结束后消息队列能够清空，系统资源能够恢复稳定。
- 不将售罄、重复购买和限购等预期业务拒绝计入技术错误率。

### 8.4 发布阻断条件

出现以下任一情况时不得发布：

- 超卖、负库存、重复订单或库存一致性差值不为 0。
- 用户能够查询或操作他人的订单、秒杀结果。
- 支付、取消、退款或超时关单造成非法状态或重复库存回滚。
- 异步消息丢失且无法补偿，或存在无法处理的持续积压。
- 压测期间出现集中 HTTP 500、应用不可用或依赖服务无法恢复。
- RR-001 库存预热覆盖问题尚未修复并完成回归验证。

## 10. 最终评审意见

本项目核心业务范围明确，用户、商品、订单、鉴权和 Redis 模式秒杀主流程已经具备实现及测试基础。秒杀系统在已验证的中等并发范围内未出现重复订单和库存差异，具备继续完善和验收的条件。

但是，2000 并发测试已确认定时库存预热与异步扣减之间存在竞态，破坏了库存一致性，并可能进一步引发超卖。该问题属于发布阻断缺陷。同时，RabbitMQ 模式、订单状态竞争和故障恢复仍缺少充分证据。

因此，本次需求评审结论为：**有条件通过**。项目可以继续进入缺陷整改和补充测试阶段；只有在阻断问题关闭、关键补测通过并形成完整证据后，才能评定为满足高并发生产发布要求。
