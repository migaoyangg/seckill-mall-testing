# 秒杀项目简历与面试说明

## 升级后的项目定位

高并发秒杀交易系统，围绕秒杀活动、Redis 预扣库存、异步创建订单、订单幂等、重复下单拦截、超时关闭和库存一致性做设计，重点解决高并发下的数据库写入压力、超卖、重复下单和失败回滚问题。

## 推荐简历写法

高并发秒杀交易系统 | Java 后端开发

技术栈：Spring Boot 3、MyBatis-Plus、MySQL 8、Redis、Lua、RabbitMQ、Redisson、JWT、Knife4j、JMeter

- 基于 Spring Boot + MySQL + Redis 构建秒杀交易系统，实现用户认证、商品管理、秒杀活动、订单创建、超时关闭等核心业务。
- 使用 Redis + Lua 实现库存校验、限购判断和库存预扣减，保证秒杀入口库存扣减的原子性，降低高峰期数据库压力。
- 将秒杀下单链路拆分为“请求受理”和“异步落单”，支持 Redis 队列与 RabbitMQ 两种削峰通道，接口快速返回 requestId，用户可查询订单创建结果。
- 设计秒杀订单幂等机制，通过 requestId、orderNo、用户-活动唯一索引和订单回查避免重复消费、重复下单和重复扣减库存。
- 基于 RabbitMQ TTL + 死信队列实现订单延迟关闭，定时任务扫描作为兜底，避免未支付订单长期占用库存。
- 设计订单状态机，覆盖待支付、已支付、已取消、超时关闭、退款中、已退款等状态，并使用支付流水号和 Redis 幂等标记处理重复支付回调。
- 增加用户维度限流、重复请求标记和失败回滚 Lua 脚本，处理入队失败、落单失败等异常场景，保证 Redis 预扣库存与 MySQL 最终落库的一致性。
- 使用 MySQL 乐观锁扣减秒杀库存，并通过唯一索引兜底防止并发下重复创建订单。
- 基于定时任务处理未支付订单超时关闭，并回补普通商品或秒杀商品库存。

## 面试可讲的核心链路

1. 用户请求进入秒杀接口，先校验活动状态。
2. Redis Lua 对用户请求做限流，防止单用户瞬时刷接口。
3. Redis setIfAbsent 写重复请求标记，避免同一用户短时间重复提交。
4. Redis Lua 原子完成库存校验、限购判断、库存预扣和购买计数更新。
5. 生成 requestId 和 orderNo，将消息写入 Redis 队列或 RabbitMQ，并把处理状态缓存为 PROCESSING。
6. 后台消费者批量拉取队列消息，调用订单服务创建秒杀订单。
7. MySQL 侧先插入订单触发唯一约束兜底，再使用乐观锁扣减秒杀库存，最后写订单明细。
8. 消费成功后更新秒杀结果为 SUCCESS；失败会重试，超过次数后执行 Redis 预扣回滚并更新结果为 FAIL。

## 可以准备的追问答案

- 为什么入口用 Redis Lua？
  Redis 单线程执行 Lua，可以把库存判断、限购判断、扣减库存和购买计数更新放在一次原子操作里，避免并发请求在 Redis 层出现超卖。

- 为什么还要 MySQL 乐观锁？
  Redis 是入口削峰和预扣，MySQL 是最终事实数据。数据库扣减仍然需要 `stock_count > 0 AND version = ?` 兜底，防止 Redis 与数据库状态不一致时产生超卖。

- Redis 预扣成功但订单创建失败怎么办？
  队列消费者会有限重试。最终失败时执行回滚 Lua，同时回补库存和用户限购计数，并删除重复请求标记。

- 如何防重复下单？
  入口有 Redis 重复请求标记，Lua 有用户限购计数，数据库有用户-秒杀活动唯一索引，消费者重复消费时会先查询已有订单并幂等返回。

- 为什么异步下单？
  秒杀瞬时流量主要压力在数据库写入。接口只做 Redis 原子预扣和入队，订单落库由后台消费者处理，可以削峰并缩短接口响应时间。

- RabbitMQ 和 Redis 队列有什么区别？
  Redis 队列实现轻量，适合本地演示；RabbitMQ 提供更完整的消息确认、消费并发和死信队列能力，更适合说明生产级削峰和延迟关单设计。项目通过 `seckill.async.mode` 做通道切换。

- 支付回调为什么要幂等？
  支付平台可能重复通知，同一个 transactionNo 重复回调时应该只生效一次。项目通过 Redis 幂等标记、订单状态判断和数据库唯一索引兜底，避免重复支付状态流转。

## 压测建议

压测前准备：

- Redis 中已预热秒杀库存。
- 秒杀活动状态为进行中。
- 准备多个测试用户 Token，避免单用户限流影响整体压测结果。
- 关注接口平均响应时间、P95/P99、Redis CPU、MySQL 慢 SQL、订单成功数和库存是否一致。

可以记录在简历或面试中的指标：

- 并发用户数，例如 200/500/1000。
- 秒杀接口平均响应时间和 P95。
- 请求成功受理数、最终订单成功数、失败原因分布。
- 秒杀结束后 Redis 库存、MySQL 库存、订单数是否满足一致性校验。

项目已提供脚本：

- JMeter: `scripts/jmeter/seckill-entry.jmx`
- wrk: `scripts/wrk/seckill.lua`
- 一致性校验 SQL: `scripts/sql/seckill_check.sql`

不要编造压测数据。真正跑过后再把数字写进简历，例如：“使用 JMeter 对秒杀接口进行 500 并发压测，接口 P95 控制在 xx ms，库存和订单数据无超卖”。
