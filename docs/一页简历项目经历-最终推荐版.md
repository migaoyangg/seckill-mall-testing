## 秒杀商城质量保障与自动化测试实践

**项目时间：** 2026.XX - 至今  
**项目简介：** 基于 Spring Boot 的电商秒杀系统，包含用户、商品、管理员、订单、支付退款和秒杀模块。围绕同一商城后端分别开展服务端接口自动化测试和 Android 客户端自动化测试，验证认证、权限、参数校验、订单状态、支付幂等、库存一致性和端到端用户流程。

**技术栈：** Java、Spring Boot 3、MyBatis-Plus、MySQL、Redis、RabbitMQ、JWT、JUnit 5、Mockito、MockMvc、pytest、requests、Kotlin、Retrofit、Appium、UiAutomator2、ADB、Allure、Jenkins

### 方向一：商城后端接口与服务自动化测试

- 梳理 Controller、Service、DTO、参数校验、权限规则、业务码和订单状态机，设计正常、异常、边界、幂等、越权和状态流转用例。
- 使用 JUnit 5、Mockito、MockMvc 编写 Service/Controller 测试，覆盖用户登录、商品缓存、管理员权限、普通订单、支付回调、秒杀预扣和库存同步等核心分支。
- 使用 pytest + requests 编写真实 HTTP 接口自动化，利用 fixture 管理普通用户/管理员账号、Token 和 Session，使用参数化复用参数校验场景。
- 通过 HTTP 状态码、业务码、响应 JSON、SQL、Redis Key、订单状态和库存变化建立结果校验链路。
- 定位并修复参数类型错误返回 HTTP 500、管理员商品路径漏拦截和 Token fixture 复用导致测试不稳定等问题，并完成回归验证。
- 已完成 Java 测试 `[35/35]`、pytest 接口测试 `[19/19]` 通过；具体数字以投递前最后一次回归为准。秒杀高并发 JMeter/wrk 结果 `[待实测]`。

### 方向二：Android 移动端自动化测试平台

**平台定位：** Android 商城 App 是首个被测应用，商城后端与方向一复用；平台独立负责 APK、设备、用例、任务、执行和报告，不修改商城业务代码。

- 使用 Kotlin + Retrofit 完成被测 Android App 的登录、商品列表/详情、下单、订单查询和退出登录，为 UI 自动化提供稳定页面和资源 ID。
- 基于 Appium 2、Python、pytest 和 Page Object 设计登录、商品浏览、商品详情、下单和订单查询等端到端测试用例。[待完成]
- 设计平台数据模型和接口，管理测试项目、App、APK 版本、测试用例、测试套件、设备和执行记录。[待完成]
- 通过 ADB 实现设备注册、状态检测、APK 安装/清理和 Logcat 获取；通过设备锁避免同一设备被多个任务并发占用。[待完成]
- 开发测试执行 Worker，负责接收任务、启动 Appium、执行 pytest、采集截图/日志并回传任务状态；支持超时、取消、失败重试和异常设备释放。[待完成]
- 接入 Allure 与 Jenkins，自动构建 APK、安装模拟器、执行回归测试、归档截图日志和生成报告。[待完成]

## 面试时的项目定位

这是一个商城质量保障项目，不是两个重复的商城项目。第一条线验证后端接口、业务规则和数据一致性；第二条线验证 Android 客户端真实交互，并把 Appium 执行过程平台化。两条线复用同一个商城后端，既减少重复开发，又能展示接口测试、服务测试、移动端 UI 自动化和测试平台开发能力。

## 项目命名建议

当前最推荐的总项目名：

> **秒杀商城质量保障与自动化测试实践**

Android 子项目在不同完成阶段使用不同名称：

- 只有 Appium 脚本和公共工具：**Android 客户端自动化测试框架**
- 实现 APK/设备/用例/任务/报告管理：**Android 移动端自动化测试平台**
- 增加 Worker、设备锁、失败重试和 Jenkins：**Android 移动端自动化测试平台与执行系统**

不要在尚未实现平台后端和执行器时写“自动化测试平台”。平台名称的可信度来自“管理 + 调度 + 执行 + 归档”闭环，而不是来自 Appium 本身。
